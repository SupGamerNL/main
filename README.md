## Adding a project

1. Open `data/projects.js`, copy an existing project block and give it a new unique `id`.
2. Fill in the name, category, description, tags, links and the `page` section.
3. Optional: put screenshots in `assets/img/` and downloads in `downloads/<community>/`, then list them in a `downloads` array (see Downloads below).
4. Run `python tools/update-site.py` (checks the entry, refreshes file sizes, the sitemap and the SEO lists).

The card on the index and the project page are generated from that one entry.

### Optional extras per project

All of these can be left out. The full explanation is in the comment at the top of `data/projects.js`.

- `status`: `"released"`, `"in-development"`, `"planned"`, `"on-hold"` or `"archived"`. Shows a status badge on the card and the page.
- `cover`: a file name from the project's screenshots folder. Without it the first screenshot is used. No screenshots, no cover.
- `support`: what the project runs on, one row per version line: `{ label?, game?, engine?, versions?, loader?, requires?, note? }`. Shown as a short line on the card, as the "Compatibility" section on the page, and it is searchable.
- `changelog`: `[{ version, date?, changes: [...] }]`, newest first. Shows a "Changelog" section.
- `timeline`: `[{ date, title, text? }]`, oldest first. Shows a "Timeline" section.

## Search and filters

The search box on the index looks through names, descriptions, categories, tags, versions, loaders, required mods, status, download labels and the material chips. A search word has to match the start of a word, so `forge` finds Forge and `neoforge` finds NeoForge, and `1.12` finds 1.12.2. Several words must all match. It works together with the category buttons. Press `/` to jump to the search box. The address updates (`index.html?q=forge&cat=Minecraft+Mods`), so a search can be shared or bookmarked.

## Adding screenshots

The quick way (needs Python and Pillow once: `pip install pillow`):

```bash
python tools/add-screenshots.py <project-id> <screenshot files or a folder>
python tools/add-screenshots.py general <screenshot files or a folder>
```

It writes the full-size WebP (max 1920px wide, quality 85) to `assets/img/<project-id>/` and the thumbnail (640px wide, quality 80) to `assets/img/<project-id>/thumbs/`, with the same file name in both, and prints the `gallery` lines to paste into `data/projects.js` (or `data/gallery.js` for `general`). Captions are left as `TODO`, since only you know what a screenshot shows. Existing files are never replaced unless you add `--overwrite`.

By hand: save the images as described above and add `{ file: "name.webp", caption: "What it shows" }` to the project's `gallery` list. Screenshots show up on the project page and in the main gallery automatically. General screenshots live in `assets/img/general/` (and `thumbs/`) and are listed in `data/gallery.js`.

## Navigation

The navigation bar is part of the HTML of every page (`index.html`, `project.html`, `gallery.html`). To add a page, add a link to the `<ul class="nav-links">` list in each of them. On phones and tablets the bar turns into a burger menu, handled by `assets/js/nav.js`.

## SEO

- Every page has its own title, description, canonical link, Open Graph and Twitter tags. `index.html` and `gallery.html` hold them in the HTML. Project pages are one template, so `assets/js/project.js` fills in the tags of the project that is open: title, description, canonical (`project.html?id=<id>`), share image (the cover or first screenshot, else `icon-image.png`) and `CreativeWork` + breadcrumb structured data.
- `index.html` carries `WebSite` (with a search action that points at `?q=`), `Person` and `ItemList` structured data, plus a plain list of all projects for visitors without JavaScript. Both are generated by `python tools/update-site.py`, so run it after changing `data/projects.js`.
- `sitemap.xml` lists the homepage, the gallery and every project page. `robots.txt` points to it.
- `404.html` is shown for addresses that don't exist and forwards the old `projects/<id>/` addresses to `project.html?id=<id>`.
- To change the site address, edit `data/config.js` and the few hard-coded `supgamernl.github.io/main` URLs in the HTML heads (search for them), then run the update script.

Known trade-off: because all project pages are one template, crawlers that don't run JavaScript (Discord, many chat apps and some social previews) see the general title and image instead of the project's. Google does run JavaScript and reads the per-project tags. A separate HTML file per project would fix that, at the cost of more files to maintain.

## Downloads

Every project can offer its files in two ways, and the project page shows a "Downloads" section with a button for each:

- **Download**: the file straight from this site, from the `downloads/` folder (a folder per community, then per project, for example `downloads/minecraft/mods/bnm/`).
- **GitHub Release**: a direct download of the same file from a GitHub Release, plus a small "Release page" link.

Both are set in the `downloads` list of a project in `data/projects.js`:

```js
downloads: [
  { label: "Hotel of Secrets", note: "Minecraft 1.8.9",
    release: { tag: "minecraft-map", asset: "Hotel.of.Secrets.zip" } }
]
```

- `file` is the path inside this repo. `release` is the Release tag and the exact asset name. Either one can be left out. `group` and `note` are optional.
- Browsers can't list folders, so every file needs one entry. Spaces, apostrophes and brackets in file names are handled by the site.
- GitHub rewrites spaces and special characters in release asset names, so give assets a clean name (letters, numbers, dashes, dots) and use that exact name in `asset`.
- Release buttons show while `RELEASES_LIVE` at the top of `data/projects.js` is `true`. Only add a `release` once that Release really exists, otherwise the button leads to a 404 page.
- Files over 100 MB can't live in the repo, so those go in a Release only (Hotel of Secrets and Veldoria do this).
- Direct link format: `https://github.com/<owner>/<repo>/releases/download/<tag>/<asset>`.
- Each file in a GitHub Release can be up to 2 GB.

### File sizes

Sizes are filled in automatically, so there is no `size` to type. `python tools/update-site.py` measures every file in `downloads/` and asks GitHub for the size of every Release asset, and stores them in `data/sizes.js`. The browser also re-checks files on this site live, so a replaced file shows its new size even before the script is run again. (A `size: "..."` on a download still works as a last-resort fallback.)

## Updating the site (upload workflow)

1. Replace changed files in the repo, delete old or renamed ones.
2. Hard refresh (Ctrl+F5) because browsers cache old files.
